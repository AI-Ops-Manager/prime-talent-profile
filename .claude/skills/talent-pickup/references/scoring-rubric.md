# マッチ度の採点軸と選定レポートの型

印象で順位を付けないための道具。各スコアには、根拠になったフィールドを必ず添える。
データで確認できないことは推測で埋めず、「不明」と書く。

## 採点軸（100点）

| 軸 | 配点 | 見るフィールド | 判断基準 |
|---|---|---|---|
| 1. 要件適合（MUSTのカバー） | 40 | aiSkills / devSkills / bio / projects | MUST を直接カバー=満点。隣接スキルでの代替=半分。根拠が薄い=1/4以下 |
| 2. 実績の関連性 | 30 | experiences / projects の**実記述** | 同種案件の実績あり=満点。類似ドメイン=6割。実績記載なし（ポテンシャル評価）=4割以下 |
| 3. 稼働リアリティ | 20 | availabilityStatus / availabilityCapacity | available かつ時間が要件以上=満点。partially / on_assignment は開始時期次第で減点。AOM 照会前は暫定 |
| 4. 案件フィット（過不足） | 10 | devSkillLevel / 経歴の格 / 案件規模 | 過不足なし=満点。軽い案件に上位レベルを当てる、格が要る案件に軽い候補を当てる、はどちらも減点 |

単価と信頼度（ランク・面談）は、この MCP からは見えないので採点に入れない。AOM への照会事項として別に書く。

### 目安

- **85以上**: 本命。筆頭に置ける
- **70〜84**: 有力。組み合わせ・面談次第
- **55〜69**: 補欠。要件緩和時や複数名体制の脇役
- **55未満**: レポートに載せない（件数だけ残す）

### 注意

- `projects[].description` が null のものは実績に数えない
- bio の完成度は実績の代理指標にならない。「bio立派×実績空」は機械的に下げる
- 「実装者かどうか」が要件なら、「統括・推進」表現と「自分で構築・実装」表現を区別して読む
- 複数名体制の案件は、個人の点数に加えて役割の補完性（上流・設計／実装／伴走・定着／現場翻訳）を組み合わせ欄で見る
- 迷ったら保守的に付ける。点数のインフレは提案の信頼を削る

## 選定レポートの型

保存先: `docs/selections/<案件slug>-YYYY-MM-DD.md`。表示名・連絡先は書かない。

```markdown
# 候補選定 — {クライアント名 / 案件名}

作成日: YYYY-MM-DD

## 1. 案件要件

- クライアント: {業種・規模}
- やりたいこと: {AI化・開発の対象}
- MUST: {箇条書き}
- WANT: {箇条書き}
- 稼働イメージ: {h/月、期間、対面・常駐の有無}
- 仮定した事項: {推測で埋めた箇所}

## 2. 母集団

- search_talents 全件: {N}名 ／ keyword で追加確認: {語と件数}
- この時点で外した人: {人数と理由（unavailable 等）}

## 3. 推奨候補

### 1. {イニシャル} — マッチ度 {N}

- UUID: {フル桁}
- 稼働: {status / capacity} ／ dev: {level} ／ ai: {level}
- スコア内訳: 要件{n}/40・実績{n}/30・稼働{n}/20・フィット{n}/10
- 推薦理由: {データの根拠を引きながら2〜3行}
- この案件で効くところ: {1〜2行}
- 懸念: {正直に。なければ「特になし」}

（候補分繰り返し。通常3名）

## 4. 補欠と見送り

- {イニシャル}: {理由}

## 5. AOM への照会事項

- 稼働の最新状態（掛け持ち・開始時期）
- 単価表示の取り決め
- 過去の見送り経緯の有無
- {役員クラスの含否など、依頼者に判断してもらう点}

## 6. 推奨アクション

- {単独か組み合わせか。組み合わせなら役割分担}
- {候補が薄い場合: 要件緩和案、AOM への追加割り当て依頼}
```
