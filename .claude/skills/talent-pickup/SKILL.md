# talent-pickup — 候補の絞り込み

割り当てられたリストは大きくない（数名〜数十名）。網羅は難しくないので、差がつくのは
「要件を先に固めること」と「一人ひとりを実績の記述で見ること」の2つ。印象で順位を付けない。

参照: [references/search-guide.md](references/search-guide.md)（ツールの仕様と読み方・案件タイプ別のキーワード例）、
[references/scoring-rubric.md](references/scoring-rubric.md)（採点軸とレポートの型）、
`docs/selection-guide.md`（4条件と外しやすいところ）。

## 0. 要件を構造化する

入力（商談メモ・依頼文・口頭）を次に分ける。

- **MUST**: 欠けたら候補外になる条件（特定のスキル・稼働時間・開始時期・常駐可否・実装を自分でやるか）
- **WANT**: あると加点される条件（業界経験・上流経験・特定ツール）
- **案件属性**: 業種・支援領域・稼働時間/月・期間・成果物型か伴走型か・単価の目安

着手に最低限要るのは「何をやってほしい案件か」と「稼働イメージ（時間か期間）」の2つ。
無いときだけ着手前に聞く。ほかは仮定を明記して進める（例:「単価の指定なし → 既定表示のまま」）。

## 1. 母集団を取る

`search_talents` を引数なしで呼び、全員を一覧にする。
一覧には `id`（フルUUID）、表示ラベル、`availabilityStatus`、`availabilityCapacity`、`devSkillLevel`、`aiSkillLevel`、スキル名を控える。
表示ラベルは作業用で、レポートにも資料にも出さない。

MUST の固有名詞（例: kintone / RAG / Salesforce）は `keyword` で一語ずつ引く。表示ラベル・自己紹介・経歴・プロジェクトの本文まで
対象になり、`matches` に当たった箇所の抜粋が返るので、ここで一次判定ができる。複数の語で当たった人は強い候補。
ただし表記ゆれ（GAS と Google Apps Script）は別々に引き、短い略語の誤ヒットは抜粋で確かめる。

`availabilityStatus` が unavailable の人は、この時点で外す（理由を残す）。

## 2. 一人ずつ読む

気になる人を上位6〜10名まで `get_talent` で読む。サマリだけで判断しない。

- `experiences` と `projects` の**両方**を読む。実績が経歴欄にしか無い人がいる
- `projects` の `description` が空のものは実績に数えない。タイトルだけ並んでいても実績空と同じ
- `bio` が立派でも `experiences` / `projects` が空なら評価を下げる。bio は実績の代理にならない
- 「統括した」「推進した」と「自分で構築した」を区別して読む。実装を自分でやる案件なら後者が要る
- `devSkillLevel` が none / vibecoding / junior の人を、単独でシステムを作り切る案件に出さない。
  逆に、要件整理や定着支援が主役の案件では上位レベルは必須ではない
- 対面・常駐の要件があるなら、所在地はデータに無いものとして「本人確認が要る」と書く

## 3. 採点する

[references/scoring-rubric.md](references/scoring-rubric.md) の4軸（要件適合 40 / 実績 30 / 稼働 20 / 案件フィット 10）で採点し、
各スコアに根拠のフィールドを添える（「projects に◯◯の実績」「experiences の description に△△」）。
データで確認できないことを推測で埋めない。

強い順に並べない。「案件にちょうど良く、確実に稼働できる順」に並べる。
役員・代表クラス（経歴の役職に代表取締役・CxO がある）は、含めてよいか依頼者に確認する。

## 4. 提示する

チャットには次だけを簡潔に出す。

1. 推奨候補（通常3名）: イニシャル・UUID・マッチ度・推薦理由（データの根拠付き）・懸念
2. 仮定した事項と、判断してほしい点（役員クラスの含否、稼働の確認、単価）
3. 補欠と、見送った人の理由（1行ずつ）

同時に選定レポートを `docs/selections/<案件slug>-YYYY-MM-DD.md` に保存する（型は rubric の末尾）。
レポートにも表示名・連絡先は書かない。

## 5. AOM に照会する（提示の前に必ず）

この MCP からは、ランク・稼働不可のフラグ・面談の有無・他案件との掛け持ちが見えない。
候補が固まったら、UUID を添えて AOM の担当に次を確認する。

- いま稼働できるか（掛け持ちの状況、開始できる時期）
- 単価表示（既定表示のままでよいか、個別の取り決めがあるか）
- 過去に別案件で見送った経緯があるか

確認が取れた候補だけを `talent-profile` に渡す。渡すときはレポートの「案件要件」と候補ごとの「この案件で効くところ」を添える。
資料の `fit`（解決できる課題）と `points`（推薦理由）は、この2つから書く。
