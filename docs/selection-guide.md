# タレント選定の進め方

AOM のタレントを案件に当てるときの判断基準。パートナー各社が候補を絞る段階で、AOM と同じ物差しを使えるようにまとめてある。
個々のタレントの実名・ランク・稼働状況は含めていない。候補の照会は AOM 側へ。

## AOM が候補を割り当てる前に見ている4条件

AOM 側では、1つでも欠けたら候補から外している。飛ばすと、提案後に「稼働できない」「面談していない」で巻き戻すことになるため。

1. **ランクが A 以上** — AOM のルーブリックで A が「案件にアサインできる」基準ライン。A 未満は、決定軸であるクライアント対峙力が未検証という意味になる
2. **稼働可能** — 稼働不可のフラグが立っていないこと。A ランクで面談済みでも、フラグが立っていれば提案できない
3. **面談済み** — 初回面談を終えていること。登録だけの人はスキルシートの自己申告しか根拠がない
4. **2つのデータソースを両方見る** — 登録情報だけ、カタログだけ、のどちらか片方では判断材料が揃わない

ランク・不可フラグ・面談の記録は AOM 側にしかなく、Prime 向け MCP からは見えない。
パートナー側でできるのは次の2つ。割り当てリストに入っている人はこの4条件を通過した前提で読んでよいこと、
ただし稼働状況は日々変わるので、提示の直前に AOM へ確認すること。

## 選定でよく外すところ

**強い人から順に出さない。** 案件に対してちょうど良く、確実に動ける人から出す。
上位ランクで引き合いの多い人を軽い案件に当てると、稼働が取れずに差し替えになる。
稼働目安が「確認中」の人より、明確に空いている人を優先する。

**稼働バッティングは記録に出てこない。** 稼働不可のフラグが立っていなくても、他社の定例に毎週出ている、
契約書のやりとりが進んでいる、といった現在進行形の稼働がある。フラグは最新とは限らないので、提案の直前に本人へ確認する。

**実装を伴う案件は実装力を個別に確認する。** 「AI導入支援」の実績があっても、実装はチームに任せていた、というケースがある。
システムを単独で作り切る案件では、`devSkillLevel` と、経歴の文中の「自分で構築した」表現を確認する。

**対面・常駐の要件があるときは所在地を本人に聞く。** 登録情報の所在地は整備されていないため、記載を信じて提案すると当日になって動けないことがある。海外在住の人もいる。

**過去に見送った理由が残っている。** 同じ候補が別案件で一度見送られている場合、その理由（オーバースペック・稼働逼迫・条件不一致）は AOM 側に記録がある。照会時に確認すれば出せる。

## 料金の考え方

パートナー名義でエンド企業に出す資料の単価表示は、AOM とのパートナー契約で決まっている（一律の表示単価か、自社の定価表か）。
表示のしかたは契約時に取り決めたものに従い、迷ったら AOM へ確認する。

- クライアントに出す資料には手数料込みの時給だけを載せる。原価の内訳は出さない
- 初期費用なし・実働ベース・月単位が基本形
- 単価を出さない運用（「商談時にご共有」）でもよい。`brand.json` の `defaults.rate` が既定の表示になる

## 候補の照会先

領域別に「誰がいて誰がいないか」の調査結果は AOM 側に蓄積がある。プールに存在しない領域もあるため、
案件が固まった段階で早めに照会してほしい。近接する経験を持つ候補を提示できる場合がある。
